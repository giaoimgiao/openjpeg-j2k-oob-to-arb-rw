# 漏洞状态、影响描述与缓解

## 1. 漏洞身份（已知漏洞）

- 根因：openjpeg J2K 的越界写 —— `read_sod()` 中用 **TLM 声明的 tile-part 数**分配
  `tp_index`，却按 **SOT 的 `TPsot`** 递增写入（`tp_index[current_tpsno]` 越界）。
- 该问题属于**已公开跟踪**的一类（OSV-2025-219 / openjpeg PR#9520 一类）。
- **因此本仓库不主张 0-day**：根因不是新发现。

## 2. 本仓库的新增内容

1. **受限原语的精确刻画**：每次越界写两个 8 字节值（内容为文件偏移量），
   自由槽 `≡8 (mod 24)`、耦合死槽 `= 前一自由槽 + 2`、以及**单调约束**。
2. **从受限写升级为任意读写**：数据导向 / 对象嫁接（`memoryview.view.buf`）。
3. **可复现的本地链路**：`repro/`（含三段越界写构造器与完整触发）。
4. **负面结论也有价值**：自然解码下 `tp_index` 的邻居是宿主进程的任意缓冲，
   ⇒ “让程序自己使用被污染对象”的通用化路径不成立（这正是远程化未解决的原因）。

## 3. 影响的准确描述（不夸大）

| 场景 | 结果 |
|---|---|
| 对解码进程 | **崩溃**（SIGSEGV / SIGABRT）或**长时间卡死** |
| 触发方式 | 单文件；任何用 PIL 解码 JP2/J2K 的入口 |
| 是否等于“服务级 DoS” | **取决于部署**：上传配额/积分、解码是否隔离子进程、
  是否有自动重启与超时 |
| 远程代码执行 | ❌ 未实现（需执行点 + 固定地址） |

> 说明：本仓库**不把“服务崩溃”当成必然结论**。
> 若目标把解码放在独立 worker 且有超时/重启，后果是**该 worker 反复失败**，
> 不是持久不可用。请按具体部署自行评估。

## 4. 下游 vendored 副本的滞后问题（值得单独指出）

- Pillow 将 openjpeg 源码 **vendored** 进 wheel（`pillow.libs/libopenjp2-*.so`）。
- 上游修复**不会自动**进入该构建产物 ⇒ 即使 openjpeg 上游已修，
  Pillow 用户仍可能受影响。
- 建议：依赖下游发行版（Pillow）对 vendored 依赖做**版本同步检查**。

## 5. 缓解措施（面向部署方）

1. 限制图片上传体积；不需要 JP2/J2K 就直接禁用该解码路径。
2. 解码放在**独立、低权限、可超时、可重启**的进程中。
3. 关注 Pillow 版本更新，尤其是其 vendored 依赖的同步情况。
4. 对解码失败的 worker 做速率限制，避免被反复触发的崩溃拖垮调度。
